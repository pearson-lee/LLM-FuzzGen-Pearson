# Role

You are an expert fuzzing engineer. Your task is to produce a **maintainable Python seed generator** for a single blocker in an existing fuzz target.

Do not just emit a few ad-hoc seeds. Emit code that can keep generating and evolving blocker-oriented seeds over time.

# Goal

Create a Python 3 generator that produces native-format seeds which are likely to:

1. Reach the blocker branch line.
2. Then cross the blocked side.

This is a blocker-branch-oriented feedback loop, not general seed generation for broad coverage.

# Target Blocker

- Project: `libpcap`
- Language: `c`
- Fuzz target name: `llm_fuzzgen0626013047`
- Fuzz target source path: `llm_fuzzgen0626013047.c`
- Target function name: `gen_prevlinkhdr_check`
- Target function signature: `struct block *gen_prevlinkhdr_check(compiler_state_t *cstate)`
- Candidate headers: `N/A`
- Source file: `gencode.c`
- API source path: `gencode.c`
- Branch line: `3149`
- Blocked side line: `3150`

# Important Principle

Generate bytes as consumed by the **existing fuzz target**.

Prefer native subformats only inside the blocker-relevant API argument slice. If the fuzz target wraps, splits,
prefixes, writes to a temporary file, null-terminates, or otherwise transforms `Data` before calling the library API,
the generator MUST reproduce that outer harness layout.

Do not choose an unrelated input format merely because another API in the fuzz target also consumes `Data`.
The runtime blocker segment determines the API anchor.

However, unlike a normal seed-generation task, your output must be a **Python generator program** that:

1. Encodes the blocker-specific insight in code.
2. Produces multiple closely related seed variants.
3. Is easy for a human to extend and maintain.
4. Uses only the Python standard library.
5. Is deterministic.

# Required Generator Interface

The generator code must be a complete standalone Python 3 script with this behavior:

1. It defines a function `build_seeds()` that returns `list[tuple[str, bytes]]`.
2. It supports `python generator.py --output-dir DIR`.
3. When executed, it writes one file per seed into `DIR`.
4. It contains concise comments that explain the blocker strategy.
5. It does not require third-party packages.

/* The main fuzzing entry point */
int LLVMFuzzerTestOneInput(const uint8_t *Data, size_t Size) {
    /*
     * We need at least enough data for a filter string, a bpf_insn,
     * and a pcap_pkthdr. This is a rough heuristic.
     */
    if (Size < sizeof(struct bpf_insn) + sizeof(struct pcap_pkthdr) + 1) {
        return 0;
    }

    /*
     * Create a "dead" pcap handle. This is essential for fuzzing because it
     * allows us to call pcap_compile and other functions without needing a
     * live network interface, which wouldn't be available in a typical
     * fuzzing environment.
     */
    pcap_t *p = pcap_open_dead(DLT_EN10MB, 65535);
    if (p == NULL) {
        /* This should not happen with pcap_open_dead, but check just in case */
        return 0;
    }

    /*
     * Fuzz Target 1: bpf_validate()
     * This function checks a raw BPF program for validity.
     * The second argument to bpf_validate is the number of instructions,
     * not the size in bytes.
     */
    const struct bpf_insn *prog_insns = (const struct bpf_insn *)Data;
    int prog_len = Size / sizeof(struct bpf_insn);
    if (prog_len > 0) {
        bpf_validate(prog_insns, prog_len);
    }

    /*
     * Fuzz Target 2: pcap_compile()
     * This function compiles a user-supplied filter string into a BPF program.
     * The filter language is complex and a great candidate for fuzzing.
     * We create a null-terminated string from the input data.
     */
    char *filter_str = (char *)malloc(Size + 1);
    if (filter_str == NULL) {
        pcap_close(p);
        return 0;
    }
    memcpy(filter_str, Data, Size);
    filter_str[Size] = '\0';

    struct bpf_program fcode;
    /* Attempt to compile the filter string */
    if (pcap_compile(p, &fcode, filter_str, 1, PCAP_NETMASK_UNKNOWN) == 0) {
        /*
         * Fuzz Target 3: pcap_offline_filter()
         * If compilation was successful, we can now test the filter against a
         * packet. We'll construct a packet header and use the rest of the
         * input data as the packet itself.
         */
        if (Size > sizeof(struct pcap_pkthdr)) {
            struct pcap_pkthdr pkthdr;
            memcpy(&pkthdr, Data, sizeof(struct pcap_pkthdr));
            const u_char *pktdata = Data + sizeof(struct pcap_pkthdr);
            pkthdr.caplen = pkthdr.len = Size - sizeof(struct pcap_pkthdr);
            pcap_offline_filter(&fcode, &pkthdr, pktdata);
        }

        /*
         * Fuzz Target 4: pcap_setfilter()
         * Test setting the compiled filter on the handle.
         */
        pcap_setfilter(p, &fcode);

        /*
         * Fuzz Target 5: pcap_dispatch()
         * Although we don't have a live capture, calling dispatch can still
         * exercise some logic with the installed filter.
         */
        pcap_dispatch(p, 1, dummy_callback, NULL);

        /*
         * IMPORTANT: Free the memory allocated by pcap_compile to avoid leaks.
         */
        pcap_freecode(&fcode);
    }

    /* Clean up the allocated string and the pcap handle */
    free(filter_str);
    pcap_close(p);

    return 0;
}

# Step 0: Blocker Input Contract

Before designing any seed family or writing generator code, you MUST first infer the blocker input contract.
This contract is the source of truth for the generator.

The runtime blocker segment is used to anchor:

1. The library API call that leads to the blocker.
2. The argument of that API that is derived from fuzzer `Data`.

The internal runtime call chain is only the observed route for the current seed. Do not assume the same internal
semantic route will reach the blocked side. If the observed route reaches the branch but not the blocked side,
find a semantic route under the same API anchor that can satisfy the predicate.

If the blocker is reached through a parser, grammar, decoder, state machine, visitor, virtual dispatch,
opcode switch, field-tag dispatch, or handler table, the contract must identify the exact input representation
category that selects the target route. Examples of representation categories include token kind, grammar
production, AST node kind, opcode, message type, field number plus wire type, chunk or marker type, header name,
command name, enum value, consume-call position, or handler key.

Do not use an input form merely because it is semantically similar to the desired value. When multiple surface
forms express the same concept, choose only the form whose parser/decoder/dispatcher route is proven to call the
target function and reach the blocked predicate.

If multiple input forms may express the same semantic concept but belong to different representation categories,
do not merge them into one family. Put each representation category in a separate seed family with a stable name
that identifies the category. The primary family should use the category with the strongest source evidence. If the
source evidence is missing or ambiguous, say `unknown` in the contract and make exploratory families explicit rather
than presenting guesses as confirmed facts.

You MUST include the following six contract items in `analysis_summary`, using these exact prefixes:

1. `[0A API Anchor]` Name the fuzz target call site that eventually reaches the blocker. Identify the
   blocker-relevant API argument.
2. `[0B Input Layout]` Describe how `Data[0..Size]` maps to that API argument. If `Data` is sliced, split,
   length-prefixed, null-terminated, written to a file, or consumed through `FuzzedDataProvider`, give the
   byte-range formula. If the whole `Data` buffer is passed verbatim, say so explicitly.
3. `[0C Predicate Setter]` Describe the input-level trigger that sets the blocked predicate to the required value.
   Do not only name an internal setter function. Name the syntax, bytes, field value, consume call, opcode,
   token/production kind, field tag, marker, command, or handler key needed to select the target route. If several
   representation categories are plausible, list them separately and state which one is source-supported for the
   target route.
4. `[0C2 Call-Site Reachability]` Setting the predicate value does NOT by itself guarantee the function that reads
   the predicate is even called. For every function on the path from the API anchor to the blocked-side predicate
   that is *conditionally called*, name the *independent input feature* required to make that call execute. This
   caller-trigger condition may be orthogonal to `[0C]`: one input feature may select an optional encapsulation,
   sub-operation, qualifier, or dispatch branch that reaches the call site, while a different feature sets the
   predicate. Use the call chain and the call-site source to name each independent caller-trigger at the input
   level (the syntax, token, field, qualifier, opcode, command, or option that causes the call). Use the
   `## Blocker function call sites` section. Build status is deterministic evidence supplied by the pipeline:
   do not infer or override it. Never select a filtered `inactive` call site. Prefer an `active` call site when its
   guard is semantically compatible. An `unknown` call site remains a hypothesis, not proof that the code exists in
   the target build; select it only when the output explicitly keeps `evidence_sufficient=false`. For selectable
   call sites, examine each guard, REJECT any whose guard is the negation of (or otherwise conflicts with) the
   required predicate value, and select a compatible one. Record the decision in the `callsite_decision` output
   field. If the blocker function is called unconditionally once the API is invoked, state that explicitly. If the
   listed call-site contexts are insufficient to decide, say `unknown` rather than assuming the function is reached.
5. `[0D Reader Path]` Describe the caller path that reads the required value at the blocked predicate. State
   whether this is the same as the observed runtime path or a different semantic route.
6. `[0E Survival Check]` Describe whether the value can survive from setter to reader. Check for reset, overwrite,
   macro side effect, early return, longjmp, cleanup, parser ordering, state pop, and lifecycle constraints.

Only after completing this contract should you design seed families. Every seed family must place the
blocker-relevant content at the byte location described by `[0B Input Layout]`, satisfy every independent
caller-trigger named in `[0C2 Call-Site Reachability]`, trigger `[0C Predicate Setter]`, and reach
`[0D Reader Path]`.

# What To Infer

From the code and blocker location, infer:

1. The exact fuzz-target input layout that materializes the blocker-relevant API argument. The inferred native
   format above is only a hint for the inner API argument, not necessarily for the entire `Data` buffer.
2. The input-level syntax, bytes, fields, or semantic values that trigger the predicate setter.
3. If a parser/decoder/dispatcher is involved, the exact representation category that selects the target function
   rather than a semantically similar route.
4. The reader path that reaches the blocked predicate after the setter fires.
5. Whether the required value survives from setter to reader.
6. Which boundary values, malformed forms, or encoding variants should be systematically generated.
7. How to organize those hypotheses into maintainable Python code instead of one-off samples.
8. Which seed families should exist so later iterations can keep, discard, or refine them without renaming everything.

# Quality Bar

The generator should:

- Focus on **high-signal blocker-specific variants**, not generic random fuzz.
- Prefer small, readable seeds.
- Include a small family of boundary cases near the blocker condition.
- Produce both likely-valid and strategically malformed inputs when useful.
- Encode the blocker reasoning explicitly in comments and helper functions.
- Generated filenames must carry a stable family tag so later iterations can measure family-level usefulness.
- Use names like `F01_structured_base_01.ext`, `F02_boundary_flags_01.ext`.
- Keep family tags stable across future revisions. Do not generate anonymous names like `seed_01.bin`.

# Output Format

Return **only** a single JSON object. No markdown fences. No extra commentary.

The JSON object must have exactly these keys:

- `analysis_summary`: array of short strings
- `failure_analysis`: array of short strings
- `family_decisions`: array of short strings
- `revision_plan`: array of short strings
- `generator_design_rationale`: string
- `generator_filename`: string
- `generator_code`: string
- `sample_seeds`: array of strings
- `callsite_decision`: object documenting the chosen blocker call site (structure below)

The first six entries of `analysis_summary` MUST be the Step 0 contract entries, in this exact order:

1. `[0A API Anchor] ...`
2. `[0B Input Layout] ...`
3. `[0C Predicate Setter] ...`
4. `[0C2 Call-Site Reachability] ...`
5. `[0D Reader Path] ...`
6. `[0E Survival Check] ...`

If any contract item is unknown, say `unknown` and explain what context is missing. Do not silently guess.

The `callsite_decision` object must have these fields (derived from the `## Blocker function call sites` section):

- `selected_candidate_id`: the chosen call site id (e.g. `gencode.c:7238`), or `unknown`.
- `observed_guard`: the guard condition at that call site as seen in its local context.
- `compatibility_reason`: why that guard is compatible with the required `[0C Predicate Setter]` value.
- `input_trigger`: the input-level feature/syntax that causes that call site to execute.
- `evidence_sufficient`: boolean; `false` if the listed local context was insufficient to decide (then do
  NOT assume the call is unconditional). It must also be `false` when selecting a call site whose
  `build_status` is `unknown`.
- `rejected_conflicting_callsites`: array of `{candidate_id, reason}` for the observed/current route and any call
  site whose guard clearly conflicts with the predicate (need not be exhaustive).

# Additional Constraints

- `generator_code` must be valid Python 3.
- `sample_seeds` must be representative outputs of the generator.
- Keep the generator compact and readable.
- If the inferred target format is text-based, emit text seeds in that native format. If binary is needed, generate bytes in Python code.
- The generated filenames inside `build_seeds()` should use the preferred extension when practical.
- Prefer deterministic systematic variants over probabilistic sampling: use range enumeration, interesting-value lists, bitflip variants, and Cartesian combinations of relevant fields. Each family should explore a meaningful range of the hypothesis space, not a single hardcoded point. For example, if a field controls a branch, enumerate all semantically distinct values for that field rather than picking one guess.
- Inside `build_seeds()`, return tuples `(filename, payload)` where `filename` preserves the stable family tag.
- Design families so some target structure reachability and some target blocker-boundary refinement, but every family must still be blocker-oriented.
- Do not generate seeds for an API path that is not on the runtime blocker segment unless the Step 0 contract explains
  why that path reaches the same blocked predicate.
- Do not treat a setter as sufficient. A seed family must also reach a reader path where the predicate reads the
  required value.
- A predicate setter is necessary but not sufficient for reachability. If the function that contains the blocked
  predicate is only called under a separate input condition (see `[0C2 Call-Site Reachability]`), every seed family
  MUST combine ALL independent caller-trigger features together with the predicate setter in the same input. The
  caller-trigger and the setter may be orthogonal input features; a seed that sets the predicate but omits a
  required caller-trigger will not reach the predicate at all. Do not drop a caller-trigger feature merely because
  it looks unrelated to the predicate value.
- Do not treat corpus-level branch reach as proof that generated seeds reached the branch. Seed families must be
  designed so their own representative seeds can reach the branch.
- If the blocker-relevant argument is a slice of `Data`, every generated seed must place the intended content exactly
  in that slice.
- If route selection depends on parsing, decoding, dispatch, or state-machine transitions, generated seeds must use
  the exact representation category that selects the blocker route. Do not substitute another representation that is
  only semantically equivalent.
- If the required route depends on tokenization, field typing, opcode/message selection, header/command naming,
  or consume-call order, encode that choice explicitly in helper names, comments, and family names.
- Do not mix distinct route-selection categories in one family. For example, if two encodings, tokens, opcodes,
  field tags, command names, or handler keys may dispatch differently, create separate families and label the route
  evidence for each family.

# Final Reminder

The main deliverable is not the seeds themselves. The main deliverable is a **maintainable blocker-aware generator** that a fuzzing pipeline can keep and evolve.
