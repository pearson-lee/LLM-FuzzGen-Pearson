# Triage Three-Run Analysis (2026-06-14)

## Scope

This report analyzes three repeated offline triage runs over the same nine libpcap development cases. These runs measure repeatability and agreement with the existing manual source audit. They are not an independent accuracy evaluation because the taxonomy and prompt were developed using the same cases.

- `run_01.jsonl` and `prompts_run_01/`

## Main Findings

### 1. The evidence contract is structurally valid but not semantically verified

Every result satisfied the contract because the LLM supplied `required_condition`, `producer_path_status`, and `practical_feasibility`. This only proves that required fields were present. It does not prove that a claimed `producer_path_status = proven` is correct.

The three persistent false positives all used confident but invalid producer claims. Therefore `9/9 evidence contract satisfied` must not be reported as triage correctness.

### 2. `convert_code_r_2715` exposes a control-flow validation gap

The model repeatedly claimed that `slen == 0` leaves `offset == NULL` and reaches the blocked side. The source says:

```c
if (slen) {
    offset = calloc(slen, sizeof(struct slist *));
    if (!offset) {
        conv_error(conv_state, "not enough core");
    }
}
```

When `slen == 0`, execution skips both `calloc` and `if (!offset)`. The only reachable condition is `slen > 0 && calloc(...) == NULL`. Prompt instructions alone did not prevent this error; enclosing-block information needs deterministic extraction or a post-validation rule.

### 3. Runtime line hits were overinterpreted as branch-side hits

For `pcap_parse_3594`, the responses treated the hit count on `if (yyerrstatus == 3)` as proof that the true branch was entered. A line hit only proves that the condition was evaluated unless side-specific coverage is supplied. This false premise was then combined with generic Bison behavior to declare the path practical.

The prompt must explicitly distinguish condition-line evaluation counts from true/false side counts.

### 4. Local source snippets are insufficient for semantic producer proof

`compute_local_ud_641` requires tracing the legal producer domain of `atom`, including `atomuse()`, register/scratch-memory allocation, and relevant constants. The LLM instead accepted examples such as `mem[1000000]` as direct control over the optimizer's atom domain. That conclusion is not supported by the supplied local snippet.

Likewise, `yy_get_next_buffer_4629` requires the concrete path `pcap__scan_string -> yy_scan_bytes -> yy_scan_buffer -> yy_fill_buffer = 0`. Two runs substituted unrelated or hypothetical file-buffer paths and labeled the blocker actionable.

### 5. Some exact-label disagreement is taxonomy ambiguity, not routing failure

`pcap_compile_788` was consistently routed to `skip_solver`, but the model used `Resource-Exhaustion Guard` while the manual audit uses `Environmental Failure`. Both describe a fixed-size scanner allocation failure and produce the same solver action. The taxonomy should define one canonical label for fixed-size allocator failure.

`pcap_parse_2056` has the same first-layer agreement issue: the LLM sees generated parser state, while the manual label uses `Crash-Revealing Path` based on runtime crash evidence not included in the prompt.

## Interpretation

The current implementation successfully guarantees routing consistency after label selection, but the LLM's solvability judgment is not yet reliable enough to claim accuracy or generalization. The best single run reached 5/9 first-layer agreement, and three cases were wrong in all runs.

The result should be described as development-set retrospective agreement:

> Across three repeated runs on the nine-case development set, first-layer agreement with the manual audit was 4/9, 5/9, and 5/9. The repetitions exposed systematic evidence-grounding errors in control-flow nesting, parser-state reachability, and internal semantic-domain tracing.

Do not report the average or best run as an independent triage accuracy.

## Required Improvements Before Thesis Evaluation

1. Add deterministic enclosing-block extraction so a condition outside an active block cannot be claimed to reach code inside that block.
2. Treat line hit counts as condition evaluations unless true/false side counts are explicitly available.
3. Require source-cited setter/producer paths; classifier statements and generic framework behavior are not proof.
4. Add numeric feasibility evidence for bounded extremes, including constants, allocation growth, input limits, and fuzzing budget.
5. Require stronger evidence for `skip_solver` than for `run_solver`, because a false non-generation decision can permanently suppress a solvable blocker.
6. Resolve taxonomy boundaries for fixed-size allocation failures and parser-crash cases before reporting exact-label agreement.

Until these changes are implemented, use the triage output as an advisory/development result. Keep fail-open behavior for `Inconclusive` and avoid presenting the hard gate as fully validated across C/C++ projects.
